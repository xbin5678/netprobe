# 数据采集流水线

从几十个公开源采集数据 → 跨源去重 → 多级可用性检测 → 导出成可直接导入的配置。

```
collect   抓台账里所有 active 源（GitHub 仓库 + 节点站 + Telegram 频道）
manage    跨源去重、入库、清理过期
check     第一级 TCP 预筛 → 第二级真实网页访问，只留真能用的
verify    对判定可用的再复核一遍，剔掉「侥幸通过」的
export    导出 clash 配置 / base64 订阅 / 明文链接
```

> **想加数据源、想看每个源的质量排名** → 看 [SOURCES.md](SOURCES.md)。
> 本文档只管「怎么跑」。

## 一键使用

**在 VPS 上**（全新机器，一条命令，无交互）：

```bash
curl -fsSL https://raw.githubusercontent.com/xbin5678/netprobe/main/deploy/bootstrap.sh | bash -s -- --domain 你的域名
```

去掉 `--domain` 就只装本机，访问 `http://<IP>:8787`。重复执行等于升级代码，`data/` 和 `config.yaml` 不会丢。
参数、成功判据、排错表都在 **[INSTALL.md](INSTALL.md)**（这份是写给 AI 和脚本看的，可以无人值守调用）。

**在本机 Windows 上**：双击 **`启动界面.bat`**，打开图形界面。

```
┌──────────────────────────────────────────────────────────────┐
│ 数据采集流水线    ● 代理未开启   32,628   124    66     -    │
│                                  库内节点 可用  有速度 耗时   │
├──────────────────────────────────────────────────────────────┤
│ [▶ 一键更新] [只采集] [检测新节点] [全量重测] [只复核] [停止]│
├──────────────────────────────────────────────────────────────┤
│ 真实网页访问                              ████████░░░░  62%  │
│ 正在验证 3200/7870 个节点能否真的打开网页…                    │
├──────────────────────────────────────────────────────────────┤
│  运行日志  │  数据源  │  可用节点  │                          │
└──────────────────────────────────────────────────────────────┘
```

三个标签页：

- **运行日志** —— 实时滚动，成功的行绿色、失败的红色
- **数据源** —— 每个源的产量、通过率、独有节点数，按通过率排序。可以勾「只看订阅仓库」过滤掉 Telegram 频道
- **可用节点** —— 每个可用节点的协议、延迟、存活时长、通过次数

进度条会显示当前在哪个阶段（采集 / TCP 预筛 / 真实网页访问 / 复核），点「停止」能真的中断。

命令行方式（无界面，适合定时任务）：

```bash
.venv\Scripts\python.exe run.py all
```

也可以双击 `一键更新.bat`，效果一样。

**平时每天跑一次就够**，增量模式约 1-2 分钟。首次运行会下载测速内核 mihomo（约 15MB）。

## 网页版（VPS / 远程 / 手机）

不想装桌面环境，或者人在外面想用手机看，就用 `web.py`：

```bash
python web.py                        # 默认 http://0.0.0.0:8787
python web.py --port 8787 --token 你的令牌
python web.py --no-auth              # 只在内网/本机，关掉鉴权
```

界面和桌面版一致：实时日志、数据源质量、可用节点筛选导出，手机上自动变窄屏布局。

工具栏把「自动」和「手动」分开了：**一键更新**是完整流水线（采集 → 检测 → 复核），
每天定时任务跑的也是它；后面几个都是你手动点的单步操作。

| 按钮 | 做什么 |
| --- | --- |
| 一键更新 | 采集 → 深度检测 → 复核，一条龙 |
| 只采集 | 只抓源，不测 |
| 快速检测 | 全库只做 TCP 握手，几秒扫完，**不改可用状态** |
| 深度检测 | 全库走真实 HTTP，通过才算可用 |
| 检测新节点 | 只测库里没测过的 |
| 复核可用 | 把当前可用的再测一遍，剔掉侥幸通过的 |

想只测某几个节点，就在「可用节点」表里勾选（表头有全选），底下会浮出一条操作栏，
选「快速检测」或「深度检测」即可。勾选的是**指纹**，传到后端走 `--fp` 白名单校验，
不合法直接拒绝，不会拼进命令行。

网页版多一个**「长期可用」**标签页：按节点**连续存活时长**分档（≥1 / 3 / 5 / 7 天），
每个档位带数量角标，专门用来找那种不容易第二天就死的节点。存活时长从节点
**由死转活的那一刻**算起，中途死一次就清零重算，并且要求至少被测通过两次。

还有一个**「订阅链接」**标签页，把节点按客户端分好，粘一次就不用再管：

| 格式 | 给谁用 |
| --- | --- |
| `clash` | Clash Verge Rev / Mihomo Party / FlClash / Stash / ClashX |
| `v2ray` | v2rayN / v2rayNG / 小火箭 / Karing / Hiddify / NekoBox（base64，通用） |
| `singbox` | sing-box / Hiddify Next / SFA / SFI（原生 JSON） |
| `surge` | Surge Mac / iOS |
| `qx` | Quantumult X |
| `plain` | 明文链接，自己挑 |

每种格式只导出该客户端**真认的协议**——Surge 没有 VLESS，圈 X 没有 VLESS 和 Hysteria2，
sing-box 没有 SSR，硬塞进去会让整份订阅导入失败。链接形如 `/sub/<key>/clash`，
`<key>` 就是凭证（不需要登录），泄露了在页面上点「重置链接」即可作废。

### 订阅哪一档，自己选

同一个 `<key>`，加一个 `?tier=` 参数就换一档，页面上点按钮就自动带上：

| 档位 | 参数 | 条件 | 说明 |
| --- | --- | --- | --- |
| 能连接 | 不带 / `?tier=alive` | 深度筛查通过 | 默认，真能上网 |
| 有下载速度 | `?tier=speed` | 最终筛查跑出吞吐 | **最少但最稳**，名字里带 `59.7MB/s` |
| 只测了端口 | `?tier=tcp` | TCP 握手成功 | 数量最多，但端口开着不代表能用 |

实测同一份库：`alive` 722 个、`speed` 18 个、`tcp` 4160 个。
页面上的按钮直接标着这三个数字——「有下载速度」那档少得刺眼，但那才是真能跑流量的。

档位还能和「连续存活 ≥ N 天」叠加：`?tier=speed&min_age=3` 就是「有速度且活了 3 天以上」。
每个客户端配一条链接，比如手机用小火箭拉 `speed` 档、电脑上 Clash 拉 `alive` 档，互不影响。

- **零第三方依赖**：标准库 `http.server` + SSE，不装 Flask / uvicorn / Node，常驻内存 35–45MB
- **跑任务的是子进程**：网页崩了不影响任务，任务崩了网页还在
- **令牌鉴权**：首次启动生成并写进 `data/web_token.txt`，也可以用 `web.token` 固定

低配 VPS 的完整部署（systemd、swap、并发怎么调、内存不够怎么办）见
**[DEPLOY-VPS.md](DEPLOY-VPS.md)**，配置用 `config.vps.yaml`。一条命令装完：

```bash
sudo bash deploy/install.sh --domain 你的域名.com --swap 2048
```

脚本会装依赖、建 venv、配 swap、装 systemd 服务、加每日定时任务，
有域名还会顺带把 Caddy 反代和 HTTPS 证书配好，最后打印带令牌的访问地址。
卸载用 `deploy/uninstall.sh`，日常运维用 `deploy/manage.sh`。

## 订阅测速页（独立页面 `/probe`）

上面那些是「自己的流水线」，这个页面是**测别人给的订阅**：贴一个订阅链接进去，
解析出节点，测能不能用、延迟多少、**下载速度多少**，结果存成历史，下次接着用。

入口在主界面右上角「订阅测速 →」，或者直接开 `https://<域名>/probe`。

### 它做四件事

1. **拉订阅**：贴链接就自动识别格式——Clash / sing-box / base64（v2rayN 那种）/
   明文 URI 列表 / Surge / Quantumult X，不用你选。拉取时带客户端 UA，不少机场
   看 UA 决定给不给内容。
2. **测节点**：分四档，随时可以只测勾选的几个。
3. **导出**：六种格式，导出的节点名里带测出来的速度（`SS-002 62.2MB/s 16ms`），
   客户端列表里一眼能看出快慢。可以只导「测出下载速度」的那几个。
4. **存历史**：每次拉取自动存一条记录，可以回来接着测、改名、删除、导出。

### 检测分四档

| 按钮 | 做什么 | 500 节点实测 |
|---|---|---|
| 自动检测 | 端口预筛 → 真实网页访问 → 给最快的 N 个测下载速度 | 3.5s + 视节点数 |
| 快速 | 只连 TCP，只看端口开不开 | 3.5 秒 |
| 深度 | 真实 HTTP 请求，通过才算可用 | 约 30 秒 |
| 测下载速度 | 按延迟排序取前 N 个，跑一遍下载 | 每个节点 1-10 秒 |

测速文件可选 **10 / 20 / 50 MB**，越小越快也越省流量。50MB × 15 个 ≈ 750MB，
低配机或者流量紧张的机器用 10MB 就够——10MB 已经能准确算出 0.1~100 MB/s 的速度了。

### 下载速度是怎么测的

mihomo 自带的 `/proxies/{name}/delay` 只给延迟，没有吞吐量。这里的做法是：

1. 把所有要测的节点一次性灌进一个 mihomo，建一个 `select` 组；
2. 测之前用 API 把组切到目标节点（`PUT /proxies/PROBE`）；
3. 通过 mixed-port 下载 `speed.cloudflare.com/__down?bytes=...` 的测试文件；
4. 读到指定字节数或超时就停，算 `字节 / 耗时`。

**一个内核测完全部节点**，不用每个节点起一次进程——低配机上那个开销很要命。
每 10 个一批，跑完一批立刻落库，中途崩了也不丢已测的结果。

「首字节」那一列是单独发一个 1 字节请求量出来的，反映的是建连 + 首包时间；
「下载速度」是扣掉建连之后的纯吞吐。

### 筛选：把「真能跑流量」的挑出来

500 个节点里，TCP 通的可能有 37 个，但**真正跑出下载速度的可能只有 3 个**。
这两件事不是一回事：

| 状态 | 说明 |
|---|---|
| TCP 通 | 端口开着而已，可能是防火墙放行、也可能是半死不活的落地 |
| 延迟低 | 只是建连快，不代表能承载流量 |
| **有下载速度** | **真的把字节搬回来了，这才是能用的** |

所以节点卡片上有一排筛选，`有下载速度` 那一档标着绿色数字，点一下只剩这一批，
并且**自动按快慢倒序排好**——最快的在最上面，直接就是你要的那几条。

配套的还有：

- `速度 ≥ N MB/s`：只留够快的，`5` 是个挺实用的门槛（能顺畅看 4K）；
- `可用`：真连测试通过的；
- `测速失败`：连得上但下载没跑通，用来排查；
- 搜索框：按名字 / 地址 / 协议过滤；
- 右侧 `测这些`：直接给**当前筛选出来的这一批**测下载速度，不用一个个勾。
  比如先点 `可用`（37 个）→ 再点 `测这些`，就跑这 37 个，不会碰另外 463 个。

筛选只影响**看得见的东西**：计数、全选、批量检测、导出都跟着变。
被筛掉的节点会自动从选中集合里退出，不会出现「点了测速，却偷偷测了一堆看不见的节点」。

导出卡片里勾上 `只导出有下载速度的`，导出的就正好是这一批。
实测：37 个可用 → 勾上后 3 个，节点名还带着 `62.2MB/s`，进客户端一眼能看出快慢。

### 订阅地址的安全处理

订阅地址是用户随手贴的，服务端要去访问它，所以：

- 只允许 `http://` / `https://`，`file://` 之类直接拒；
- 解析域名后检查 IP，**内网段（127/10/172.16-31/192.168/169.254/100.64 和 IPv6 私有段）一律拒绝**，
  免得这个接口被当成内网扫描器；
- 单文件最多 8MB，超过就报「不像订阅文件」；
- 证书错误、连不上、超时都有对应的人话提示，不会甩一个 traceback。

### 编辑功能

- 记录：改名、删除（连同里面的节点一起删）
- 节点：改名、删除、勾选批量删除
- 勾选后可以直接对选中的节点跑快速 / 深度 / 测速

### 命令行也能用

```bash
# 直接给链接，自动建一条记录并跑完整流程
.venv\Scripts\python.exe run.py probe --url "https://xxx/sub?token=xxx" --mode auto --size 10 --max-speed 15

# 对已有记录重测（--ids 只测指定节点）
.venv\Scripts\python.exe run.py probe --run 3 --mode speed --size 20
```

数据存在 `data/probe.db`，和主节点库 `data/nodes.db` 完全分开，互不影响。
测速任务用自己的一把锁（`data/probe.lock`），所以**可以和每日定时任务同时跑**。

## 界面里直接导出

「可用节点」页有一排筛选 + 导出控件：

```
分类 [全部▾]  数量 [全部▾]  延迟 [不限▾]  格式 [Clash 配置（完整）▾]
                                    [📋 复制到剪贴板]  [💾 导出文件]
```

**筛选同时作用于表格和导出**——界面上看到几行，导出的就是那几个。

| 控件 | 选项 |
|---|---|
| 分类 | 全部 / vless / vmess / trojan / ss / ssr / hysteria2 / tuic |
| 数量 | 全部 / 最快 10 / 20 / 50 / 100 |
| 延迟 | 不限 / ≤800ms / ≤1500ms / ≤3000ms |
| 格式 | Clash 配置（完整）/ 仅节点列表（YAML）/ base64 订阅 / 明文链接 |

**四种格式的差别：**

- **Clash 配置（完整）** —— 含 `proxy-groups` 和 `rules`，整份替换客户端配置
- **仅节点列表（YAML）** —— 只有 `proxies:` 一段，合并进已有配置
- **base64 订阅** —— v2rayN / Karing / Shadowrocket 从剪贴板导入
- **明文链接** —— 一行一个 URI，自己拆分或喂给脚本

复制走 Win32 API，**关掉界面内容也还在**（Tk 自带剪贴板在程序退出后会失效）。

**双击某一行**复制单个节点链接，**右键**可复制选中行。

导出的都是**成功节点**（真连测试通过的），死节点不会出现。

## 关于代理：开不开都行，行为不一样

**采集阶段**受影响，**检测阶段不受影响**。

| | 代理关闭 | 代理开启 |
|---|---|---|
| 36 个订阅仓库 | ✅ 正常抓（GitHub 走镜像） | ✅ 正常抓 |
| 154 个 Telegram 频道 | ⏭ 自动跳过 | ✅ 正常抓 |

工具会自动探测代理端口有没有在监听，关着就直接跳过 TG 源，不会卡住等超时。

**检测不用关代理。** 因为 TCP 预筛用的是原始 socket，真连测试是 mihomo 自己连出去的，
两条路都不经过系统代理，测出来的结果是真的。

### 配置代理端口

`config.yaml`：

```yaml
fetch:
  proxy: "socks5h://127.0.0.1:10808"   # v2rayN 的 SOCKS 端口
```

Clash 用户填 `http://127.0.0.1:7890`。

**注意别填环境变量里那个**（`echo %HTTPS_PROXY%` 显示的那个）。那可能是别的软件留下的，
填错了会表现成「代理明明开着但什么都连不上」。不确定就自己找：

```bash
netstat -ano | findstr LISTENING
curl -x socks5h://127.0.0.1:10808 https://www.google.com/generate_204
```

返回 204 就是对的。

## 单独跑某一步

```bash
.venv\Scripts\python.exe run.py all        # 一条龙（默认增量）
.venv\Scripts\python.exe run.py all --full # 一条龙，全量重测（约 10 分钟）
.venv\Scripts\python.exe run.py collect    # 只抓取
.venv\Scripts\python.exe run.py check      # 只检测
.venv\Scripts\python.exe run.py verify     # 只复核
.venv\Scripts\python.exe run.py speed      # 只做最终筛查（测下载速度）
.venv\Scripts\python.exe run.py stats      # 看库里现状
```

常用参数：

| 参数 | 作用 |
|---|---|
| `--limit 500` | 本次最多测 500 个（赶时间用） |
| `--top 100` | 只导出最快的 100 个 |
| `--unchecked` | 只测没测过的（断点续测） |
| `--fast` | 快速检测：只做 TCP，秒级出结果，**不改可用状态** |
| `--slow` | 深度检测：走真实 HTTP 请求（默认行为，写出来只是为了和 `--fast` 对称） |
| `--fp a1b2,c3d4` | 只测这几个指纹（网页里勾选节点用的就是这个） |
| `--type vless,ss` | 只测某几种协议 |
| `--scope alive` | 测哪一批：`all` / `alive`（只测当前可用的）/ `dead`（只捞死的）/ `new`（没测过的） |
| `--no-real` | 跳过真连测试，只做 TCP 预筛（快但不准） |
| `--full` | 全量重测，忽略增量 |
| `--no-speed` | `all` 时跳过最终筛查（省流量） |

```bash
# 快速扫一遍全库，看哪些端口还开着（几十秒）
.venv\Scripts\python.exe run.py check --fast --scope all

# 只重测某 3 个节点
.venv\Scripts\python.exe run.py check --fp a1b2c3d4e5f6,a1b2c3d4e5f7 --fast

# 给可用的节点测一遍下载速度（默认前 30 个，约 1 分钟）
.venv\Scripts\python.exe run.py speed
.venv\Scripts\python.exe run.py speed --limit 60   # 多测一些
```

## 检测是怎么做的

检测分**三档**，从便宜到贵，一档比一档严格：

| | ① 快速筛查 | ② 深度筛查 | ③ 最终筛查 |
|---|---|---|---|
| 网页按钮 | 快速检测 | 深度检测 | 测下载速度 |
| 做什么 | 只做 TCP 握手 | TCP 预筛 + 真实 HTTP 请求 | 真跑一遍 10MB 下载 |
| 耗时（400 节点） | 约 5 秒 | 约 40 秒 | 30 个约 1 分钟 |
| 能回答 | 端口还开着吗 | 这个代理真的能上网吗 | 它真能承载流量吗 |
| 结果存在 | `tcp_ok` / `tcp_ms` | `alive` / `latency` | `speed` / `ttfb` |
| 改不改「可用」状态 | **不改** | 改 | 不改（只写速度） |

三档是**漏斗**关系，不是三选一：先用①把几万个砍到几千，②再把几千砍到几百，
③只给其中最值得看的几十个测真实吞吐。**订阅页可以只订阅其中任意一档。**

快速检测的结果单独存在 `tcp_ok` / `tcp_ms` 两列里，网页「可用节点」表的 **TCP** 列就是它。
之所以不改可用状态，是因为端口开着不等于代理能用 —— 很多节点服务器上跑着别的 Web 服务，
443 永远通，但代理协议早死了。拿 TCP 结果覆盖可用状态会把一批死节点洗成「可用」。

### 第一级：TCP 预筛

400 线程并发握手，3 秒超时。便宜，先砍掉大半死节点。实测通过率 30-40%。

域名会先批量并发解析（带 25 秒总期限）—— 因为 `socket.create_connection` 的 timeout
**不管 DNS**，域名多的时候 `getaddrinfo` 能卡好几分钟，不处理的话这一步会莫名其妙慢十倍。

### 第二级：真实网页访问

把通过的节点灌进 mihomo 内核，调用 `/proxies/{name}/delay` 接口，**真的发一次 HTTPS 请求**
（默认 `https://www.gstatic.com/generate_204`，失败再试 `cp.cloudflare.com`）。

这一步才叫「能用」。因为很多节点 TCP 端口是开的（服务器跑着别的 Web 服务），
但代理协议根本没跑 —— 端口开着 ≠ 服务活着。

### 第三级：最终筛查（测下载速度）

「能上网」和「能承载流量」还是两回事。有些节点能打开 `generate_204`（返回 204，几乎没数据），
但一跑真流量就卡死、被限速、或者几百字节之后断掉。所以最后一步是**真的下载一个 10MB 文件**，
算 `字节 / 耗时`。

做法和第二级共用同一套内核：把候选节点灌进一个 mihomo，建 `select` 组，
`PUT /proxies/PROBE` 切到目标节点，再通过 mixed-port 下载 `speed.cloudflare.com/__down?bytes=...`。
**一个内核测完全部**，不用每个节点起一次进程。

只测「延迟最好的前 `count` 个」（默认 30），不是全测——10MB × 几万个是几个 TB 的流量。
实测 30 个跑 60 秒、约 200MB 流量，18 个测出速度。

两个防坑细节：

- **不足 128KB 不算数**。有的节点会先吐 364 字节然后卡死，用这个算出来是 0.0003 MB/s，
  毫无意义还会混进「有速度」那一档。现在记成「只收到 364 字节」并归为失败。
- **测速失败不清空「可用」状态**。测速超时可能只是这一轮网络抖动，不代表节点死了；
  但它确实不该出现在「有速度」那一档里，所以 `speed` 归 NULL、`alive` 保持不动。

### 节点消毒：一个坏节点会拖垮一整批

mihomo 加载配置是**全有或全无**的：200 个节点里只要有一个字段不合法，整份配置加载失败，
这一批 200 个全部被判死。公开节点里什么垃圾都有，所以入库和检测前都要过一遍
`nodehub/normalize.py`。

实测 3.2 万节点的库里，164 个批次有 **24 批整批失败**（约 4800 个节点被无辜判死），
错误全是这几类：

| 症状 | 原因 | 处理 |
|---|---|---|
| `invalid REALITY short ID` | `short-id: 08` 被 YAML 输出成数字 | `nodehub/yamlutil.py` 强制给所有字符串值加引号 |
| `unsupported xtls flow type` | 残留 `xtls-rprx-origin` / `direct`（早废弃） | 不在白名单就清空 |
| `unknown method: chacha20-poly1305` | ss 里正确写法是 `chacha20-ietf-poly1305` | 别名映射 |
| `'h2-opts.path' expected type 'string'` | path 写成了数组 | 取第一个元素 |
| `invalid REALITY public key` | 公钥不是合法 base64 / 解出来不是 32 字节 | 校验失败就丢掉该字段 |

修完再跑：164 批 **0 失败**。另外还会顺手修 UUID 大小写/缺横线、server 带方括号或末尾点、
`network: raw` 之类的别名、ALPN 里的垃圾值，SS cipher 不认识的直接丢弃。

### 复核

`check` 跑完会有十几个节点「侥幸通过」（测试那一刻刚好通，随后就死）。`verify` 再测一遍剔掉。

### 失败计数

不是一次失败就判死。`fail_threshold` 默认连续失败 3 次才降级，避免网络抖动误杀。

## 调参

`config.yaml`：

| 参数 | 默认 | 说明 |
|---|---|---|
| `fetch.mirrors` | gh-proxy / ghproxy / jsdelivr | GitHub raw 镜像。`ghfast.top` 已拉黑 |
| `fetch.concurrency` | 16 | 抓取并发 |
| `check.tcp.threads` | 400 | TCP 预筛并发，网络差就调小 |
| `check.real.threads` | 48 | 真连并发，调大更快但可能误判超时 |
| `check.real.chunk` | 250 | 一次灌给 mihomo 的节点数，低配机调到 60-100 |
| `check.real.timeout_ms` | 5000 | 单节点超时 |
| `check.real.max_latency` | 3000 | 延迟超过这个数视为不可用 |
| `check.real.retest_days` | 3 | 增量模式下，超过这么多天没测的也重测 |
| `check.speed.enabled` | true | 是否跑最终筛查（测下载速度），关掉就省流量 |
| `check.speed.count` | 30 | 最多给多少个节点测速（按延迟从快到慢取） |
| `check.speed.size` | 10 | 测速文件大小 MB，10 / 20 / 50，越大越准越费流量 |
| `check.speed.max_sec` | 12 | 单个节点最多测多久 |
| `check.speed.chunk` | 10 | 一批灌几个节点，坏节点最多带走 9 个 |
| `export.max_latency` | 5000 | 导出时过滤掉太慢的 |
| `store.prune_days` | 7 | 多少天没被任何源收录就自动清理 |

## 加数据源

**不要直接改 config.yaml**，改台账：

```bash
.venv\Scripts\python.exe tools\sources_tool.py add 名字 https://订阅地址
.venv\Scripts\python.exe tools\sources_tool.py sync    # 自动探测并回填
```

或者让工具自己找：

```bash
.venv\Scripts\python.exe -u tools\discover.py --days 3 --stars 10 --add
```

## 现状与预期

节点库 3 万多个，但**能用的只有一两百个**——这是公开节点的真实比例，不是工具的问题。

| 指标 | 实测值 |
|---|---|
| TCP 预筛通过率 | 30-40% |
| 真连通过率（占 TCP 通过的） | 3-30%，**看源** |
| 最终可用 | 100-150 个 |

**源质量差异极大**：小型精选源通过率 30-55%，大型合集仓库只有 0.5-3%。
所以台账按「独有 × 通过率」排序，产量大的源不一定有价值。详见 SOURCES.md。

## 注意

- 这些是**公共公开节点**，流量经过陌生人的服务器。**别用来登录网银、支付、公司邮箱**。
- 节点寿命很短，几小时到几天。想稳定就每天跑一次，或者自建。
- 库里的节点会越来越多，`prune_days` 会自动淘汰长期没出现的。
